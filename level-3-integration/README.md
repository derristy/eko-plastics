# Уровень 3 — Интеграция с SalesDrive и Діловод

Laravel 13, база MySQL. Форма с валидацией отправляет заявку в SalesDrive, оттуда контакт уходит в Діловод, а доступность обоих API проверяется по расписанию с оповещением в Telegram.

Демо: https://eko-plastics-integration.derristy.com

```
composer install
cp .env.example .env
php artisan key:generate
php artisan migrate
php artisan serve
```

Доступ к базе и ключи API прописываются в `.env` — `DB_*`, `SALESDRIVE_API_KEY`, `DILOVOD_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`. Без них форма и валидация работают, но заявки будут висеть в очереди с ошибкой отправки.

Чтобы заявки уходили, нужен воркер очереди и планировщик:

```
php artisan queue:work
* * * * * cd /path && php artisan schedule:run >> /dev/null 2>&1
```

## Валидация и защита от спама

Имя и фамилия — только буквы, апостроф и дефис, юникодные, так что «Іван» и «О'Коннор» проходят, «Іван123» нет. Телефон приводится к `+380XXXXXXXXX` и проверяется по списку кодов украинских операторов, поэтому `+79161234567` и `+380121234567` отклоняются. Те же правила продублированы на клиенте, но серверная проверка не зависит от клиентской.

Капчи нет. Вместо неё три вещи: скрытое поле `company`, которое человек не видит и не заполняет, а бот заполняет — такие заявки отклоняются; отметка времени открытия формы, отправка быстрее трёх секунд считается ботом; ограничение в 10 запросов в минуту с адреса.

## SalesDrive

Заявки создаются запросом на `/handler/` с ключом в заголовке `X-Api-Key` — тем же, что выдаётся в разделе API. Отдельный ключ веб-формы не нужен: формы в SalesDrive рассчитаны на их iframe и своего ключа не выдают. Создание заявки через `/api/order/*` невозможно — там есть только `update`, который требует существующий заказ, а `create`, `add` и `insert` не реализованы.

В ответе приходит `{"success":true,"data":{"orderId":N}}`, этот номер сохраняется в заявке. В `externalId` уходит наш id, по нему вебхук находит заявку.

## Как идут данные

Заявка сразу пишется в базу и ставится в очередь, поэтому форма отвечает мгновенно и ничего не теряется, если внешний сервис лежит. Дальше `SendLeadToSalesDrive` создаёт заявку и по успеху ставит `SendContactToDilovod`, который заводит контрагента в справочнике `catalogs.persons`. У обеих задач пять попыток с паузами 10 секунд, минута, пять и пятнадцать минут. Когда попытки заканчиваются, статус в базе становится `failed`, а в Telegram уходит сообщение с текстом ошибки.

## Діловод

Контрагент создаётся методом `saveObject` в справочнике `catalogs.persons`. Категория «Клієнт» из ТЗ задаётся полем `parent` — это группа справочника, её id лежит в `DILOVOD_PERSON_GROUP`. Поле `personType` отвечает не за категорию, а за тип лица: `1004000000000035` — фізична особа, `1004000000000034` — юридична.

Телефон и email передаются в поле `details` одной JSON-строкой. Одноимённые поля `phone` и `email` в этом справочнике через API не заполняются: запрос отвечает `ok`, а значения остаются пустыми, поэтому контакт уходил бы без телефона.

Права API-узла настраиваются в роли пользователя, который указан в самом узле (`catalogs.APINodes`, поле `user`), а не в том, от чьего имени вы вошли. Без доступа к `catalogs.persons` любой запрос возвращает `Access to catalogs.persons denied`.

## Вебхуки

Кроме цепочки задач есть эндпоинт `POST /api/salesdrive/webhook` — SalesDrive умеет дёргать его при добавлении и смене статуса заявки. Он находит заявку по `externalId` или по id заказа и ставит задачу в Діловод, если она ещё не отработала. Если задан `SALESDRIVE_WEBHOOK_SECRET`, запрос проверяется по заголовку `X-Webhook-Secret`.

## Мониторинг

`php artisan integrations:check` пингует оба API и запускается планировщиком каждые пять минут. Сообщение в Telegram отправляется один раз при падении и один раз при восстановлении, а не каждые пять минут — состояние держится в кеше.

## Тесты

```
php artisan test
```

Восемь тестов: приём заявки, отсев цифр в имени, отсев неукраинских номеров, срабатывание ловушки, отсев слишком быстрой отправки и постановку задачи в Діловод после успешного ответа SalesDrive.

## Настройки под конкретную базу

Идентификаторы `DILOVOD_PERSON_TYPE` и `DILOVOD_PERSON_GROUP` зависят от конкретной базы Діловода и вынесены в `.env`. Группу для клиентов нужно создать в справочнике контрагентов и подставить её id.
